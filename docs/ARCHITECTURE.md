# Architecture

## Overview

```
┌──────────────── Chrome (leetcode.com tab) ────────────────┐
│ page-hook.ts (MAIN world)                                 │
│   observes /problems/*/submit/ and                        │
│   /submissions/detail/<id>/check/ responses               │
│        │ window.postMessage (submission events)           │
│ leetcode-bridge.ts (isolated content script)              │
│   correlates submit+check, verifies via LeetCode GraphQL, │
│   fetches problem metadata                                │
└────────│──────────────────────────────────────────────────┘
         │ chrome.runtime.sendMessage
┌────────▼──────── Extension service worker ─────────────────┐
│ persistent sync queue (chrome.storage.local)               │
│ retry/backoff via chrome.alarms · notifications · OAuth    │
└────────│──────────── HTTPS + session bearer token ─────────┘
┌────────▼──────── Backend (Express + PostgreSQL) ───────────┐
│ auth · repository config · sync · problems · revisions     │
│ GitHub token encrypted at rest (AES-256-GCM)               │
│ repository generator (pure functions, DB → files)          │
│ git committer (Git Data API, one atomic commit per sync)   │
└────────│───────────────────────────────────────────────────┘
         ▼
      GitHub
```

Workspaces:

| Path              | Purpose                                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------------------- |
| `packages/shared` | Domain rules shared by both sides: languages, slug/ID/path formatting, statuses, API contracts (zod) |
| `backend`         | OAuth, persistence, sync orchestration, repository generation, GitHub API access                     |
| `extension`       | Submission detection, offline queue, popup dashboard, options page                                   |

## Key design decisions

### 1. One canonical directory per problem; everything else is an index

`problems/0001-two-sum/` is the only place a solution lives. Topics, patterns, difficulty and
language pages are Markdown indexes that link to it. The directory name is computed once
(`pad4(frontendId)-slug`) and stored on the problem row, so a later title change rewrites the
README but never moves the directory.

### 2. The database is the source of truth; the repository is a projection

Every file the extension manages is generated by pure functions from database state
(`backend/src/modules/generator`). A sync never "patches" Markdown in place; it regenerates the
affected files and lets Git decide whether anything changed. This gives:

- **Deterministic output** – the same DB state always produces byte-identical files (sorted
  lists, no timestamps of generation).
- **Free idempotency at the Git layer** – the new tree is built on top of the current tree; if
  its SHA equals the parent tree's SHA, no commit is created.
- **Easy repository switching / repair** – `POST /sync/full` re-projects everything.

The only file merged rather than owned is the root `README.md`: the generated content lives
between `<!-- leetcode-sync:start -->` / `<!-- leetcode-sync:end -->` markers so a user's own
README text is never overwritten.

### 3. Two-phase sync: record, then project

```
POST /api/v1/sync/problem (idempotencyKey = "submission:<leetcodeSubmissionId>")
  │
  ├─ sync_jobs row claimed (unique per user+key) ── duplicate? return stored result
  │
  ├─ Phase 1 – one DB transaction
  │    upsert problem + topics (catalog)
  │    insert submission  ON CONFLICT (user, leetcode_submission_id) DO NOTHING
  │      └─ only a *new* submission increments counters / revisions
  │    accepted? upsert solution(problem, language) per update policy
  │
  ├─ Phase 2 – GitHub projection (skipped when nothing is dirty)
  │    dirty = solution.code_hash ≠ solution.synced_code_hash
  │          ∨ solution.synced_repository_id ≠ active repository
  │          ∨ user_problem.metadata_dirty
  │    generate files → create tree (base = head tree) → tree unchanged? stop
  │    create commit → fast-forward ref (retry on concurrent push)
  │
  └─ mark solutions synced (hash + repo + commit), job = succeeded
```

Because phase 2 is derived from state rather than from the request, retrying after any partial
failure is safe: counters are never double-incremented (unique submission ID), and a commit that
already landed produces an identical tree on retry, so no duplicate commit is made.

Identical resubmissions update counters in the database but leave every solution clean, so no
commit happens (rule 5). The repository's `metadata.json` counters catch up with the next real
commit, or immediately if the user enables **Commit metadata-only changes**.

### 4. Atomic multi-file commits via the Git Data API

A sync touches the problem directory, several indexes, the root README and stats. Writing those
with the Contents API would produce one commit per file and leave a half-updated repository on
failure. Instead the committer creates one tree and one commit and moves the branch ref with
`force: false`. If someone else pushed meanwhile, GitHub rejects the fast-forward and the
committer rebuilds on the new head (up to 3 attempts). An in-process per-user mutex serialises
syncs so the common case never conflicts.

### 5. Topics, patterns and custom tags are separate concepts

| Concept     | Source                        | Scope          | Stored in                           |
| ----------- | ----------------------------- | -------------- | ----------------------------------- |
| Topics      | LeetCode (`topicTags`)        | global catalog | `topics`, `problem_topics`          |
| Patterns    | user (optional topic mapping) | global names   | `patterns`, `user_problem_patterns` |
| Custom tags | user                          | per user       | `custom_tags`, `user_problem_tags`  |

User edits never modify official topics. When **Suggest patterns from topics** is on, a new
problem gets patterns only for LeetCode topics that _are_ patterns (e.g. "Sliding Window",
"Two Pointers", "Union Find"); nothing is guessed from the problem text.

### 6. Submission detection without DOM scraping

LeetCode's UI changes often; its network protocol changes rarely. A MAIN-world script wraps
`fetch`/`XMLHttpRequest` and only _reads_ responses of two endpoints:

- `POST /problems/<slug>/submit/` → request body has `lang`, `question_id`, `typed_code`;
  response has `submission_id`.
- `GET /submissions/detail/<id>/check/` → final state with `status_code` (10 = Accepted, 11 =
  Wrong Answer, 12 = MLE, 13 = OLE, 14 = TLE, 15 = Runtime Error, 20 = Compile Error).

"Run code" requests use `runcode_…` IDs and are ignored. The isolated content script then
confirms the submission with LeetCode's `submissionDetails` GraphQL query (which also protects
against forged `postMessage` events) and loads problem metadata via the `question` query. All
LeetCode-specific knowledge lives in `extension/src/leetcode/`; when LeetCode changes, that
directory is the only thing to update.

### 7. Never lose a solution

Detected submissions go into a persistent queue in `chrome.storage.local` _before_ any network
call. The service worker drains it, removes an item only after the backend confirms, and
re-schedules with exponential backoff (`chrome.alarms`) on network errors, 5xx and rate limits
(honouring GitHub's reset time). Permanent errors (e.g. validation) are parked with a readable
message and can be retried or discarded by the user. The idempotency key makes every retry safe.

### 8. Credentials

The GitHub OAuth token never reaches the browser. The extension holds only a revocable backend
session token (stored as a SHA-256 hash server-side). See [SECURITY.md](SECURITY.md).

## Error model

Every failure is an `AppError` with a stable `code` (see `packages/shared/src/errors.ts`), an
HTTP status, a human-readable message and a `retryable` flag. GitHub HTTP failures are
translated once in `github/github-errors.ts`:

| GitHub response                      | Code                       | Message shown                                                      |
| ------------------------------------ | -------------------------- | ------------------------------------------------------------------ |
| 401                                  | `GITHUB_AUTH_EXPIRED`      | GitHub authorization has expired. Please reconnect GitHub.         |
| 403/429 + `x-ratelimit-remaining: 0` | `GITHUB_RATE_LIMITED`      | GitHub rate limit reached. Sync will resume at HH:MM.              |
| 403 otherwise                        | `GITHUB_PERMISSION_DENIED` | No write access to owner/repo…                                     |
| 404 on repository                    | `GITHUB_REPO_NOT_FOUND`    | Repository not found — deleted, renamed, or private without access |
| 404/422 on branch ref                | `GITHUB_BRANCH_NOT_FOUND`  | Branch "x" does not exist in owner/repo                            |
| network / 5xx                        | `GITHUB_UNAVAILABLE`       | GitHub is temporarily unavailable. Your solution is queued.        |

The extension maps codes to UI messages and decides between retry and "needs attention".

## Revision model (v1)

- A **revision session** is an accepted submission made ≥ 12 hours after the previous accepted
  one, or a manual "Mark revised". `revisionCount` counts sessions including the first solve.
- Status: `new`, `solved`, `revised`, `need_revision`, `difficult`, `mastered` — set
  automatically on solve/revise, always overridable by the user.
- **Due for revision**: `need_revision` → now; `difficult` → 3 days; `new`/`solved` → 7 days;
  `revised` → 14 days; `mastered` → 60 days after the last solve/revision.

The `revisions` table stores every event, so a spaced-repetition algorithm can later be swapped
in (`revision-policy.ts`) without a schema change.

## Repository layout produced

```
<root>/
├── README.md                 # managed block: progress, topic/pattern/language tables
├── problems/0001-two-sum/
│   ├── README.md             # title, links, topics, patterns, tags, solutions, user complexity/notes
│   ├── metadata.json         # schemaVersion 1, counters, languages, timestamps
│   ├── solutions/python.py
│   └── attempts/2026-10-01-python.py   # only when the user saves an attempt
├── topics/README.md, topics/array.md, …
├── patterns/README.md, patterns/sliding-window.md, …
├── difficulty/easy.md, medium.md, hard.md
├── languages/python.md, cpp.md, …
└── stats/stats.json
```

Index directories are fully owned: an index file whose category no longer has problems is
deleted in the same commit. `problems/` is never pruned.

## Extending

- **Other platforms**: add a module next to `leetcode` in the extension and a `source` column on
  `problems`; generator and sync are platform-agnostic.
- **Spaced repetition**: replace `computeDueAt` in `revision-policy.ts`.
- **GitHub App instead of OAuth App** (per-repository permissions): implement the same
  `GitHubTokenProvider` interface; nothing else depends on the token type.
